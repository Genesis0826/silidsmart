# Business Analysis Frameworks

## Description
Provides the business analysis methods used to shape requirements, scope, process understanding, prioritization, and risk analysis. Choose a framework because it helps answer a question clearly, not because it looks complete on paper. This guidance helps move from vague requests to a concrete business case, user need, and measurable outcome.

## Workflow
1. Clarify the problem, the stakeholders, and the expected business outcome.
2. Choose the framework that fits the question instead of forcing one method everywhere.
3. Turn the analysis into implementable requirements, stories, or decisions.
4. Validate the result with project goals and constraints.
5. Document assumptions and unresolved questions.
6. Make sure the result can be used directly in project plans and documentation.

## Rules
- Use user stories, use cases, and acceptance criteria for requirement definition.
- Use SWOT, PESTLE, root cause analysis, or gap analysis when evaluating business context.
- Use BPMN, SIPOC, or value stream mapping when the process needs to be understood.
- Use decision trees or cost-benefit analysis when a choice needs to be justified.
- Use the power-interest matrix to reason about stakeholders.
- Use risk matrices for risk prioritization.
- Use MoSCoW or Kano when prioritizing requirements.
- Keep the output practical enough that engineering and QA can use it directly.
- Keep the analysis connected to the project's scope.

## Decision brief for analytical work

Apply disciplined decision framing through a brief scaled to the request, using existing requirements/evidence records:

- Decision-maker/user and the action or choice to support, including its timing.
- Observed symptom and its source; proposed explanations remain hypotheses.
- Business objective and measurable outcome, baseline/comparison population, period, target units and constraints. Distinguish relative percent changes from percentage points.
- Analytical question/target, grain and available evidence; state missing data, assumptions and dependencies before selecting a model or platform.
- Separate technical/analytical acceptance from business impact. Passing a model test or delivering a dashboard does not prove measured operational outcomes; that needs measured operational outcomes and a defensible evaluation design.
- Named implementation owner and applicable decision/approval owner. Reuse accepted scope and session authorization.

Use [analytics frameworks](analytics-frameworks.md) for method/metric contracts. For teaching or instruction evaluation, use [analytics lesson coaching](analytics-lesson-coaching/SKILL.md).

## Project Use
- Keep requirements tied to measurable project and business value.
- Prefer simple, testable outputs that the delivery team can use immediately.
- Do not over-model when the problem only needs a clear story and acceptance criteria.
